# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is primarily backend/startup hardening (onboarding
gate source of truth, async container init). The **only** UI surface in
scope is the full-screen store-failure error state (`StartupErrorView`,
STARTUP-03) that replaces the two `fatalError()` call sites in
`drinkpulseApp.swift:59,68`. STARTUP-01 and STARTUP-02 have no visible UI
delta — D-11 explicitly rules out any new loading UI this phase. This
UI-SPEC is deliberately scoped to one screen; no other screens are
in-flight for this phase.

## Design System

| Property | Value |
|----------|-------|

## Spacing Scale

Native SwiftUI note: `ContentUnavailableView` owns its own internal icon/title/description/actions spacing (framework default) — this phase does not author custom stack spacing inside it. The declared scale below exists only as a fallback if the executor needs to wrap or pad anything (e.g. the diagnostic-detail text) beyond what `ContentUnavailableView` provides by default.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Icon-to-label gaps (only if any custom sub-layout is added) |
| sm | 8pt | Compact spacing between action buttons, if stacked |
| md | 16pt | Default horizontal inset for the diagnostic-detail block, if custom |
| lg | 24pt | Not expected to be needed — reserve only if a custom container is added around `ContentUnavailableView` |

Exceptions: none. Do not introduce a custom fixed-pixel layout — let `ContentUnavailableView` center and size itself; it already adapts to Dynamic Type and screen size.

## Typography

Native SwiftUI note: sizes are Dynamic Type **text styles**, not fixed px — they scale automatically up to accessibility size AX5 (CLAUDE.md accessibility mandate). "Base pt" below is the reference size at the default (Large) Dynamic Type setting, for calibration only — never hardcode these numbers.

| Role | Text Style | Base pt (Large) | Weight | Line Height |
|------|-----------|------------------|--------|-------------|
| Title (error heading) | `.title2` (via `ContentUnavailableView`'s built-in label styling — framework default, do not override with a custom `.font()`) | ~22pt | framework default (bold) | framework default |
| Body (error description) | `.body` | 17pt | regular (400) | system default (scales with Dynamic Type) |
| Button label ("Try Again" / "Share Diagnostic Details") | `.body` weight `.semibold` | 17pt | semibold (600) — matches the existing convention at `HistoryView.swift:137,152` (`.font(.body.weight(.semibold))`) | system default |
| Diagnostic detail text (copy-paste category string) | `.caption` (monospaced digit not required — it's a short label, not a number) | 12pt | regular (400) | system default |

Exactly 2 authored weights: **regular (400)** for body/diagnostic text, **semibold (600)** for both action button labels. The title's bold weight is framework-owned (`ContentUnavailableView` default) and is not a third authored weight — do not add a third custom weight anywhere on this screen.

## Color

Native SwiftUI note: colors are semantic iOS system colors + the app's existing `DesignSystem/` palette (`DPColors.swift`, `DPBrand.swift`), not arbitrary hex — this preserves light/dark-mode adaptivity and matches every other screen.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `Color(.systemBackground)` (framework default, unmodified) | Full-screen background — D-11 requires the existing background to simply "hold"; do not introduce a new background color for this screen |
| Secondary (30%) | `.secondary` (secondary label color, framework default via `ContentUnavailableView`) | The description body text |
| Accent (10%) | `Color.accentColor` / `dpAccent` (`DesignSystem/DPBrand.swift`) | Reserved **only** for the "Try Again" button. Nothing else on this screen is accent-tinted. |
| Destructive | `dpRed` (`DesignSystem/DPColors.swift`) | **Not used on this screen.** No destructive action exists in this phase (D-07 — no "Erase and start fresh" option). Do not tint the warning icon or any text red — keep the framework-default neutral/secondary tone. Tinting it red would misrepresent severity and contradict D-08's deliberately generic, non-alarming copy. |

Accent reserved for: the single primary "Try Again" button — no other element (icon, title, description, diagnostic-share button) is accent-colored. The "Share Diagnostic Details" action is a secondary/tertiary action and should use a plain/bordered (non-accent-filled) button style so the visual hierarchy reads Retry-first.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **"Try Again"** — retry button label (localization key `startup.error.retry`). While in flight: button content swaps to a `ProgressView()` and the button is disabled (D-10); accessibility label stays "Retry loading your data", with `.accessibilityValue("In progress")` while retrying so VoiceOver users get the state change without a label swap. |
| Empty state heading | **Not applicable this phase.** D-11 explicitly adds no new empty/loading UI; the `.loading` state reuses the existing system launch background verbatim (no text, no spinner, no branding — that's Cluster B's `2026-07-27-branded-static-launch-screen.md` todo, out of scope here). |
| Empty state body | Not applicable — see above. |
| Error state | **Heading:** "Couldn't Load Your Data" (localization key `startup.error.title`). **Body:** "Something went wrong opening the app's data. Tap Try Again, or share the diagnostic details below if the problem continues." (localization key `startup.error.body`). Matches D-08's required generic tone — never mentions `RecoveredStores`, file paths, or SQLite/Core Data internals. |
| Destructive confirmation | **Not applicable this phase.** No destructive action is offered (D-07 — deliberately deferred, not omitted forever). If a future phase adds an "Erase and start fresh" escape hatch, it needs its own confirmation copy at that time — do not add one now. |
| Diagnostic/report action | **"Share Diagnostic Details"** (localization key `startup.error.contact`) — deliberately NOT worded "Contact Support" or "Report a Problem," since no live support channel exists yet (D-06); the label must not imply one. Implemented as a `ShareLink` (or equivalent copy-to-clipboard affordance) surfacing only the coarse, non-PII category string, e.g. **"Error code: STORE_UNAVAILABLE"** or **"Error code: UNKNOWN"** — never `error.localizedDescription`, never a file path, never a stack trace (Pitfall 1 / CLAUDE.md logging rules apply to UI text, not just `os.Logger`). |

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | root-state-switch | ✅ covered | D-11: `.loading` state shows the existing system launch background unchanged — no new UI, no spinner, no branding this phase. |
| error | root-state-switch | ✅ covered | D-05/D-06: `.failed` state replaces the entire app content with `StartupErrorView` (full-screen `ContentUnavailableView`), never an `.alert()` over stale content. |
| overflow | root-state-switch | dismissed | Reason: the root switch is a 3-case enum with no scrollable nav chrome — "overflow" (the nav-kind sense of truncating menu items) does not apply to a full-screen state swap. |
| long-text | root-state-switch | dismissed | Reason: no nav-level labels exist in this screen (no title bar, no back button per D-07's "no escape" requirement). |
| overflow | error-message | 🧪 backstop | CLAUDE.md mandates Dynamic Type up to AX5; the title/description must wrap (not clip) at AX5 sizes without pushing the action buttons off-screen. `ContentUnavailableView` is expected to handle this by default (it's the framework's own accessibility-adaptive layout), but this is not visually verified yet — held out as a backstop: verify at AX5 in a Preview or Accessibility Inspector session before sign-off, per CLAUDE.md's "Test layouts at largest sizes." |
| long-text | error-message | ✅ covered | Copy is short and fixed by D-08 (generic, one to two sentences) — no user-generated or variable-length content ever appears in this text. |
| long-text | retry-action, diagnostic-action | ✅ covered | Both button labels are short, fixed, English-only strings ("Try Again", "Share Diagnostic Details") — never truncate at any Dynamic Type size. |

Not raised (out of relevance filter): `empty` (no form/list-collection/media element on this screen), `populated` / `zero-one-many` (no list-collection), `partial` (no form).

**Related open topic (not part of the closed 8-category taxonomy, but explicitly locked by CONTEXT.md D-10):** the retry button's in-flight/loading micro-state (spinner + disabled) is a domain/UX-level async-loading consideration, not a `nav`/`list-collection` loading state — it's covered above under the Copywriting Contract's Primary CTA row and must be implemented exactly as D-10 specifies (disable + inline spinner, no attempt counter per D-09).

## Additional Implementation Notes (non-template, load-bearing)

- **No custom transition/animation on the state switch.** The `Group { switch containerState { ... } }` should not have an authored `.transition()`/`.animation()` beyond SwiftUI's implicit default — CLAUDE.md requires honoring `reduceMotion`, and the simplest way to satisfy that here is to not author any custom motion at all for a screen that only changes 0-2 times per app lifetime.
- **No `NavigationStack` wrapper around `StartupErrorView`.** Per D-07, there is deliberately no way to navigate away from this screen except a successful Retry — no back button, no tab bar, no dismiss gesture.
- **Accessibility labels required on both actions** (CLAUDE.md "every interactive element has a meaningful `accessibilityLabel`"): Retry → "Retry loading your data"; Share Diagnostic Details → "Share diagnostic details for troubleshooting". Neither is optional.
- **Contrast:** using only system semantic colors (`.primary`, `.secondary`, `Color.accentColor`, `Color(.systemBackground)`) already satisfies CLAUDE.md's 4.5:1 / 3:1 minimums in both light and dark mode — do not introduce a custom color pairing that would need independent contrast verification.
