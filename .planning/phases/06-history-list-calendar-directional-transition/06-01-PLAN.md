<objective>
Wrap `HistoryView.body`'s existing `switch segment { }` with a directional
`.transition(.asymmetric(insertion: .move(edge:), removal: .move(edge:)))`,
driven by a `selectSegment(_:)` handler that computes direction and mutates
`segment` in the same synchronous scope, gated by the existing
`accessibilityReduceMotion` ternary pattern from `OnboardingView.swift`
(D-01, D-02, D-03, D-04, D-05). List, Calendar, and the empty state all
flow through the same single switch, so no state, content type, or
special-casing is required to make the empty state participate identically
to populated content.

This is the phase's tracer: Task 1 wires the complete path — Picker tap →
`selectSegment(_:)` → synchronous direction computation → `reduceMotion`-
gated animated mutation → `.transition` render — end-to-end for every
segment (list, calendar, empty), proven by the existing
`test_segmentSwitch_togglesListAndCalendar` UI test plus two new unit
tests for the pure direction function. Task 2 expands automated coverage
onto the specific risk classes RESEARCH.md and the UI-SPEC identified
(alternating/rapid taps, empty-state transitions, a larger dataset) and
resolves the two genuinely manual-only checks (visual direction
correctness, HIST-03's real-device flicker check) via `<human-check>`.

Purpose: today `HistoryView` swaps List and Calendar content with an
abrupt cut. This phase makes the switch read as directional navigation —
matching the milestone's "native iOS 26 feel" goal — without touching the
underlying `@Query` fetch logic in either child view.

Output: `HistoryView.swift` gains `insertionEdge`/`reduceMotion` state, a
pure `edge(forEntering:)` helper, and a `selectSegment(_:)` handler wired
to the `Group { switch segment { ... } } .transition(...)`; a new
`HistoryViewTests.swift` unit-tests the pure direction function; the
existing `HistoryInteractionUITests.swift` gains a small, additive
`launchApp(dataset:)` signature and internal-visibility bump; a new
`HistoryInteractionUITests+DirectionalTransition.swift` adds four UI tests
covering alternating direction, rapid taps, the empty state, and a
larger dataset.
</objective>

## Research Open Questions — Resolution Approach

RESEARCH.md left two open questions to planning; both are resolved by this
plan's design rather than left for the executor to decide:

- **Open Question 1** ("does `.id(segment)` need to be added?"): resolved
  per RESEARCH.md's own recommendation — no, omitted entirely. Not exercised
  further by this plan.
- **Open Question 2** (`Picker(selection: $segment)` vs. an intercepted
  handler): resolved in favor of converting `segmentPickerRow`'s binding to
  `Binding(get:set:)` calling `selectSegment(_:)`, rather than
  `.onChange(of: segment)`. This routes every selection change (including
  non-tap sources, e.g. VoiceOver) through one synchronous function, which
  is the most direct way to satisfy Pitfall 1's ordering constraint — no
  `.onChange` lag window to reason about at all.
