<objective>
Give the onboarding gate one authoritative source of truth: `onboardingDone`
(`@AppStorage`) becomes the only thing that decides `RootShellView` vs
`OnboardingView`, and a live `@Query profiles` result can never flip it again.
Fix the adjacent unsaved-insert timing gap in `UserProfileStore.fetchOrCreate`,
add a regression test hook + UI test that proves the invariant end to end, and
document the contract in a new ADR.

Purpose: today, `RootShellView.swift:97-99` resets `onboardingDone = false`
whenever `profiles.isEmpty` is momentarily true — including on a single
transient empty render before the store settles — silently kicking a fully
onboarded user back to `OnboardingView`. This plan removes that reverse-write
so `onboardingDone` is write-only from an explicit user action.

Output: `RootShellView.swift` and `UserProfileStore.swift` fixed in place; a
new `UITestSeed` hook + `OnboardingAuthorityUITests.swift` proving the fix;
`docs/decisions/0012-onboarding-single-source-of-truth.md`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI-test launch arguments (`-dp_uitest*`) → app runtime | Process-argument-gated test hooks; resolved once from an immutable, process-scoped value; absent in production/App Store builds |
| SwiftData `ModelContext` (on-device) → `RootShellView`/onboarding gate | Local-only persistence; no network boundary is crossed by this plan |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Tampering | `UITestSeed.deleteProfileMidSession` / `RootShellView.deleteProfileMidSessionIfUITest()` | high | mitigate | Double-gated on `UITestSeed.isActive` (derived once from the immutable `-dp_uitest` process argument, never present in App Store builds) AND the new `-dp_uitest_delete_profile_midsession` flag — identical convention to the existing `forceShowOnboarding`/`seedPendingOpenInsights` hooks; inert whenever either gate is false. |
| T-3-02 | Denial of Service | `RootShellView.swift` onboarding gate (post D-01) | medium | accept | A user could theoretically end up with `onboardingDone = true` and zero `UserProfile` rows (e.g. an out-of-band store wipe outside any in-app action this plan adds), with no in-app recovery path in this phase. Accepted per CONTEXT.md's scoping: recovery is explicitly deferred to a not-yet-built delete-all-data flow (ADR-0012, decision 3); this plan does not introduce any new way to reach that state — it only stops treating a transient query result as if it were that state. |

</threat_model>
