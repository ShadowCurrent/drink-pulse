## Motion & Transition Contract

> This is the actual design contract for Phase 6. It supplements the base UI-SPEC template
> because this phase's substance is animation/interaction, not visual chrome. Values here are
> prescriptive — the planner and executor should treat them as the source of truth, not
> starting points for further exploration.

### Transition mechanism (locked — D-01)

- Wrap the existing `Group { switch segment { case .list: listContent; case .calendar: calendarContent } }` in `HistoryView.body` with:
  ```swift
  .transition(.asymmetric(
      insertion: .move(edge: insertionEdge),
      removal: .move(edge: insertionEdge == .trailing ? .leading : .trailing)
  ))
  ```
- `List` and `ScrollView` are treated as opaque subviews under a single transition — **no
  snapshot/rendering hack, no `.id(segment)`** (redundant per research: switch-case branches
  resolving to different concrete view types already have distinct SwiftUI structural identity).
- `calendarNavHeader` stays **inside** `calendarContent` (not hoisted out of the sliding
  container) — matches current code shape, no reason found to change it.

### Direction semantics (locked — D-03)

| From | To | Insertion edge (new content enters from) | Removal edge (old content exits to) |
|------|-----|---------------------------------------------|----------------------------------------|
| List | Calendar | `.trailing` (right) | `.leading` (left) |
| Calendar | List | `.leading` (left) | `.trailing` (right) |

`HistorySegment.allCases == [.list, .calendar]` is the source of truth for spatial order — List
is the left/leading segment, Calendar is the right/trailing segment. Direction always follows
segmented-control spatial position, never a fixed "forward/back" independent of picker order.

### Animation curve (Claude's discretion, resolved here)

Reuse the exact curve already established in `OnboardingView.swift:80` — do not invent a new one:

```swift
.spring(response: 0.4, dampingFraction: 0.8)
```

### Reduce Motion (locked — D-04, HIST-02)

With `accessibilityReduceMotion` true: **instant cut, no slide at all** — not a faster/shorter
animation, a bare state mutation outside `withAnimation`. Reuse `OnboardingView.swift`'s ternary
shape verbatim:

```swift
@Environment(\.accessibilityReduceMotion) private var reduceMotion

private func selectSegment(_ new: HistorySegment) {
    insertionEdge = (new == .calendar) ? .trailing : .leading
    if reduceMotion {
        segment = new
    } else {
        withAnimation(.spring(response: 0.4, dampingFraction: 0.8)) {
            segment = new
        }
    }
}
```

### Ordering constraint (research-derived — critical, not optional)

Direction state (`insertionEdge`) **must** be computed in the same synchronous scope as the
`segment` mutation — both inside (or immediately before) the same function/`withAnimation` block.
Do not split "read old segment, compute direction" and "commit new segment" across two separate
SwiftUI update cycles (e.g., do not compute direction inside a lagging `.onChange` closure that
fires after `segment` has already re-rendered once). Getting this wrong produces a real, Apple-
Forums-documented bug: alternating switches (List→Calendar→List→Calendar) show the second and
later transitions sliding the *wrong* direction, even though the first switch looks correct.
`Picker(selection: $segment)`'s direct two-way binding has no such hook by default — planning
must convert the trigger to either an explicit `selectSegment(_:)` function (shown above) or
`.onChange(of: segment) { old, new in withAnimation { ... } }`, verifying ordering either way.

### Empty state (locked — D-05, HIST-03)

The empty state (`earliestEvent == nil`, rendered via `emptyState` inside `listContent`)
participates in the **same** transition container as populated content — no special-cased
instant swap. Switching List↔Calendar while in the empty-data state slides directionally exactly
like the populated case.

### Known risk requiring on-device verification (not resolvable by spec alone)

`List` (UIKit-backed, used by `HistoryListQueryView`) and `ScrollView` (used by `calendarContent`)
are structurally different view types. Every switch back to `.list` fully reinitializes
`HistoryListQueryView`, including its `@Query` — this is expected SwiftUI/SwiftData behavior, not
a bug, but it means HIST-03's "no layout pop, flash, or `@Query` re-fetch flicker" criterion can
only be confirmed by running the built feature on a real device with a realistic dataset (the
existing UI-test seed of exactly one event is too small to surface this). This UI-SPEC does not
resolve that question — it is explicitly a verification-gate item, not a design decision (see D-02
fallback: snapshot-based crossfade, only if the native transition is found to visibly pop/flash).
