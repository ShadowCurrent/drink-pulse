<objective>
Close UAT gaps G-05-4 and G-05-5, both diagnosed in
`.planning/debug/insights-chart-scrub-marker-height-and-missing-x-value.md`
as two independent defects in the identical scrub pattern shared by
`AlcoholAreaChart` and `WeekdayBarChart`:

1. **Constant marker height (G-05-4)** — `RuleMark(x: .value(...))` is
   declared with no `yStart`/`yEnd`, so per Apple's own documentation it
   spans the entire plotting area; `.annotation(position: .top)` therefore
   anchors to the plot's top edge, a constant screen Y for every touched
   X, never the datum's own value. Neither chart has a `PointMark`.
   Confirmed on-device: pixel-identical annotation Y for a 0.0-value point
   and the dataset's peak.
2. **Invisible callout / missing X value (G-05-5)** — the callout renders
   zero pixels. `.dpGlassCard(.chip)` → `.glassEffect(.regular, in:)` does
   not composite inside a Swift Charts `.annotation`; confirmed by an
   on-device single-variable isolation probe and corroborated by Apple DTS
   (Developer Forums thread 788041: "Generally speaking, Liquid Glass is
   not a part of Swift Charts" / "currently, there's no dedicated support
   for liquid glass effects in Charts"). `.regularMaterial` was also
   probed and is equally broken there (renders an opaque black rectangle).
   Only an opaque `Color` background renders correctly. Because the
   callout is fully invisible (not just missing the date), the user's
   report that "only the X value is missing" is explained by two
   aggravating conditions: `InsightsHeroCard`'s 40pt headline already
   shows the Y value during a scrub, and Month's thinned X-axis (5 labels
   across ~31 bands) can't substitute for the date either — Week's 7-for-7
   labels happen to mask the defect there.

The debug session verified the fix direction end-to-end on device (not
merely reasoned about): bounding the `RuleMark`, adding a `PointMark` at
the datum with `.annotation` moved onto it, and swapping the callout's
background to an opaque `Color` together produced a marker at the correct
data height and a fully legible date+value callout at every tested X.

Both gaps share this one root pattern and are fixed identically on both
charts (D-04's "identical treatment" requirement) — one plan, one task per
chart file, not split by gap.

Purpose: the scrub callout is the only way a user reads an exact value off
either Insights chart (CHART-01, the phase's core requirement). As shipped
by 05-03-PLAN.md it fixed the flicker/clip symptom but left the marker's
height meaningless and the callout invisible — the phase's stated goal
("read exact per-point values") is not yet met.

Output: `AlcoholAreaChart.swift` and `WeekdayBarChart.swift` both gain a
`PointMark` at the selected datum carrying the `.annotation`, a bounded (or
removed, per chart) `RuleMark`, and an opaque-background callout via a new
`DPGlass.swift` modifier — with 05-03's `yDomainUpperBound` headroom and
Reduce Motion gating preserved unchanged.
</objective>

## Gap Closure Context

Both gaps were diagnosed in one debug session
(`.planning/debug/insights-chart-scrub-marker-height-and-missing-x-value.md`),
which used on-device XCUITest screenshot diagnostics (stationary long-press
at multiple X positions) plus a four-variant single-variable isolation
build to separate the marker-anchoring defect from the glass-rendering
defect, then verified the combined fix direction on-device with a probe
build before recording it. Neither defect is a regression introduced by
05-03-PLAN.md — 05-03 only removed the overflow-squeeze that had
previously masked both, which is why they surfaced immediately after it
shipped.

This project has no automated visual-diff harness for Swift Charts
annotations (05-RESEARCH.md's Validation Architecture, reconfirmed by this
debug session and by `InsightsScrubUITests.swift`'s own code comment that
annotation content does not surface in the accessibility tree). The
`<automated>` commands below are regression guards (build + the existing
scrub test suite stay green) — they cannot see a marker's screen height or
a callout's pixel content. The `<human-check>` block in each task is the
actual proof for G-05-4/G-05-5 and must be completed on-device before this
plan is considered resolved.
