# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note (read first):** This phase is native iOS `UILaunchScreen` config — a
pre-process, OS-rendered static bitmap (Info.plist `UIImageName`/`UIColorName` keys
resolved against the Xcode Asset Catalog), not a SwiftUI view and not a web/React
surface. There is no npm/shadcn ecosystem in this project (`drinkpulse` is a native
Swift/SwiftUI app — confirmed no `components.json` or `package.json` at the repo
root). Several standard UI-SPEC categories (spacing scale, typography scale, 60/30/10
palette, third-party registries) do not literally apply to a one-color-plus-one-icon
static bitmap with zero interaction and zero text. Each section below states its
adapted contract explicitly rather than being silently omitted, so the checker's six
dimensions still have an explicit PASS condition to verify against.

All visual decisions in this contract are already locked in
`04-CONTEXT.md` (D-01 through D-04) and confirmed by `04-RESEARCH.md` —
no open design questions remain for this phase; this document restates
those decisions in contract form for the planner/executor/checker.

## Spacing Scale

Standard 8-point spacing scale does not apply — this is a single centered image on a
flat background, not a layout with multiple elements. The only spatial contract is
icon size/placement:

| Token | Value | Usage |
|-------|-------|-------|
| Icon placement | Centered (horizontal + vertical) | D-03 — matches Apple HIG's default `UIImageName` centering behavior |
| Icon size | Matches the real Home Screen icon's on-screen size exactly — not full-bleed, not enlarged, no custom scale factor applied beyond what Icon Composer's export already encodes | D-03 |
| Safe area | `UIImageRespectsSafeAreaInsets` not required to be forced `false` unless Xcode's generated default clips the centered icon — verify visually; default HIG placement already centers within safe area | Research Pattern 1 |

Exceptions: none.

**Load-bearing verification note (not a spacing exception, a risk):** 04-RESEARCH.md
flags a documented Icon Composer export bug where "File → Export" flattened PNGs omit
the platform icon margin, making the exported image look larger/differently-cropped
than the real Home Screen icon. Because D-03 requires an exact on-screen-size match,
this is captured as a backstop item in UI Considerations below — not something this
contract can resolve on paper, only something execution must visually diff.

## Color

Not a 60/30/10 app-surface palette — this screen is exactly two flat color values
(one background, resolved per appearance) plus one multi-layer gradient icon asset.
Both values are locked by D-01/D-04 to be a zero-diff match with existing app code,
not a new design choice.

| Role | Value | Usage |
|------|-------|-------|
| Background — Light (Any Appearance) | `srgb(1.000, 1.000, 1.000)` / `#FFFFFF` | Full-screen background, matches `Color(.systemBackground)` in light mode exactly (D-01) |
| Background — Dark | `srgb(0.000, 0.000, 0.000)` / `#000000` | Full-screen background, matches `Color(.systemBackground)` in dark mode exactly (D-01) |
| Icon (only image element) | `icon.json` linear-gradient: `display-p3(0.212, 0.878, 0.812)` → `srgb(0.145, 0.388, 0.922)` (teal → blue), flattened from the two-layer `drinkpulse-3-pulse.svg` + `drinkpulse-2-drop.svg` composition | The static launch-screen image — must be pixel-equivalent to the real Home Screen `AppIcon`, per D-02 (no simplified/single-layer mark) |
| Rejected: brand accent (`AccentColor`) | `srgb(0.980, 0.365, 0.212)` (coral) | Explicitly rejected for the background per D-01 — would require also changing `.loading`'s background in `drinkpulseApp.swift:75`, which is out of scope this phase. Do not use coral anywhere on this screen. |
| Destructive | not applicable | No destructive action exists on a static launch screen |

Accent reserved for: nothing — there is no accent color, no interactive element, and
no 10% highlight on this screen. The only "color" decision is background-continuity
with `.loading`, and the icon's own pre-existing gradient (not a new palette choice).

**Asset Catalog contract (names the executor MUST use, so `UIImageName`/`UIColorName`
resolve — Pitfall 4 in 04-RESEARCH.md: a misnamed reference silently fails with no
build error):**

| Asset | Type | Name | Contents |
|-------|------|------|----------|
| `LaunchBackground.colorset` | Color Set | `LaunchBackground` | Any Appearance = white `1.000/1.000/1.000`; Dark = black `0.000/0.000/0.000` (hardcoded literals per A2 in 04-RESEARCH.md's Assumptions Log — spot-check against a running `Color(.systemBackground)` on-device before final commit, do not assume the hex is exactly right without a color-picker check) |
| `LaunchIcon.imageset` | Image Set | `LaunchIcon` | Flattened static export of `AppIcon.icon`, "Any Appearance" (+ optional separate "Dark" rendition only if Icon Composer/Xcode auto-derives one distinctly — D-04 forbids hand-designing new dark artwork) |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Standard web-shaped
> states (empty/loading/error list states, long-text truncation, zero-one-many
> collections) mostly do not apply to a static pre-process bitmap with no data and
> no text. The considerations below are the platform-appropriate equivalents:
> appearance variance, cross-frame visual continuity, and config/asset-reference
> failure modes — the real "states" a launch screen can be in.

Applicable state considerations resolved: 2 covered, 3 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| Light/Dark appearance | Background color, icon rendition | ✅ covered | Background is defined as two explicit appearance variants (white/black) in `LaunchBackground.colorset`, per D-01/D-04; the icon uses whatever dark rendition Icon Composer/Xcode auto-derives — no new artwork is designed (D-04), so there is no unresolved appearance branch. |
| Static-only (no animation/spinner/wordmark) | Whole screen | ✅ covered | Explicit contract in Copywriting Contract above: `UILaunchScreen` is platform-static by design; REQUIREMENTS.md forbids animation/spinner/text outright. Config review of the `project.pbxproj`/Info.plist diff is the verification method (no runtime test possible — confirmed in 04-RESEARCH.md's Validation Architecture). |
| Cross-frame flash/continuity ("loading" transition) | Launch screen → `.loading` (`Color(.systemBackground)`, `drinkpulseApp.swift:75`) → first live frame | 🧪 backstop | Statement: "The launch screen's background is visually indistinguishable from `.loading`'s `Color(.systemBackground)` and from the first live frame's background, on a genuine force-quit cold launch on a real device." No automated test can observe the pre-process bitmap (XCUITest attaches after process start — confirmed in 04-RESEARCH.md's Don't-Hand-Roll table), so this can only be a human real-device verification backstop, never a silent pass. |
| Icon size/margin fidelity vs. real Home Screen icon | `LaunchIcon.imageset` | 🧪 backstop | Statement: "The flattened `LaunchIcon` renders at the same on-screen size/crop as the real Home Screen `AppIcon`, with no extra margin or enlargement." 04-RESEARCH.md's Pitfall 1 documents a known Icon Composer export bug (no-margin PNGs); this must be visually diffed against a real Home Screen icon screenshot before acceptance — it is not resolvable from this spec alone. |
| Asset-name-reference correctness (`UIImageName`/`UIColorName` exact string match) | `LaunchIcon`, `LaunchBackground` names wired into the Info.plist/build settings | 🧪 backstop | Statement: "The `UIImageName`/`UIColorName` values in the compiled Info.plist exactly match the Asset Catalog entry names `LaunchIcon`/`LaunchBackground`, with `INFOPLIST_KEY_UILaunchScreen_Generation` removed from both Debug and Release configs." A typo here silently falls back to the blank default (Pitfall 2 + 4 in 04-RESEARCH.md) with no build error — must be confirmed by inspecting the actual `project.pbxproj` diff, not assumed correct. |
